# 题目：数据库索引原理

## 问题
请阐述数据库索引的底层原理，重点说明 B+Tree 的结构与优势，聚集索引（Clustered Index）与非聚集索引（Secondary Index）的区别，最左前缀原则的工作原理，以及常见的索引失效场景。

## 考点
- B+Tree 的数据结构与为什么选择它
- 聚集索引与非聚集索引的存储差异
- 联合索引的最左前缀原则
- 索引覆盖（Covering Index）
- 索引失效的典型场景
- 回表查询的代价

## 解答

### 一、为什么使用 B+Tree

数据库索引需要支持：
1. **等值查询**：`WHERE id = 100`
2. **范围查询**：`WHERE id > 100 AND id < 500`
3. **排序**：`ORDER BY id`

**候选数据结构的淘汰**：

| 数据结构 | 查找 O | 范围查询 | 原因淘汰 |
|---------|--------|--------|---------|
| 哈希表 | O(1) | ❌ 不支持 | 无法范围查询，不适合磁盘 |
| 二叉查找树 | O(log n) | ✅ | 数据在磁盘上，树太高导致多次磁盘 I/O |
| 平衡二叉树 (AVL) | O(log n) | ✅ | 同上，树太高 |
| 红黑树 | O(log n) | ✅ | 同上，且更新旋转复杂 |
| B 树 | O(log n) | ✅ | 非叶子节点也存数据，数据量大时节点数多 |
| **B+Tree** | O(log n) | ✅✅ | **最优** |

**B+Tree 的优势**：

```
对比 B 树：
┌──────────────────────────────────────────────┐
│ B 树：               B+ 树：                  │
│                                             │
│     磁盘块                          磁盘块    │
│   ┌─────────┐                   ┌─────────┐  │
│   │ K1 V1 K2..│  ← 数据在非叶子  │ K1 K2...│  ← 非叶子节点只有 key
│   └──┬───┬───┘                   └──┬──┬───┘  │
│      │   │                          │  │      │
│   ┌──┘   └──┐                  ┌────┘  └────┐ │
│   ▼         ▼                  ▼            ▼ │
│ 叶子节点存数据              叶子节点存数据     │
│                           (且有链表串联！)    │
│                           ┌──┐ ┌──┐ ┌──┐   │
│                           │D1│→│D2│→│D3│   │ ← 双向链表
│                           └──┘ └──┘ └──┘   │
└──────────────────────────────────────────────┘
```

**B+Tree 优于 B Tree 的原因**：

1. **非叶子节点不存数据，只存 key**：单个磁盘块能放更多索引项 → **树更矮** → 磁盘 I/O 更少（这是根本原因）

2. **叶子节点形成有序的双向链表**：范围查询极快——定位到起始 key 后顺链表遍历即可，无需回溯

3. **稳定性**：所有数据查找最终都需要到叶子节点 → **查找效率稳定**（B Tree 可能在内节点就命中）

4. **叶子节点之间的指针**用于范围查询和全表扫描（按索引排序）

**数据举例**（假设磁盘块 16KB，key 8B + 指针 6B）：
- B+Tree：一个非叶子节点大约 16KB / 14B ≈ **1170 个索引项**
- 3 层 B+Tree：1170^2 × 16 ≈ **2200 万行**数据
- 这意味着 2200 万行的表，主键查询只需 **2-3 次磁盘 I/O**

**MySQL InnoDB 的 B+Tree 特点**：
- 叶子节点存储完整行数据（针对聚集索引）
- 叶子节点之间有双向链表（page header 中记录前后 page 指针）
- 页（Page）大小默认 16KB，是 InnoDB 存取的基本单位

### 二、聚集索引 vs 非聚集索引

| 维度 | 聚集索引 (Clustered Index) | 非聚集索引 (Secondary Index) |
|------|--------------------------|---------------------------|
| 数据存储位置 | 叶子节点 = 整个数据行 | 叶子节点 = 索引列 + 主键值 |
| 数量限制 | 每个表只能有 1 个（数据只能按一种顺序存储） | 可以有多个 |
| 查询效率 | 回表次数少（数据就在索引中） | 可能需要回表（再到聚集索引查数据） |
| 更新的影响 | 可能导致页分裂和行移动 | 相对较轻 |
| InnoDB 默认创建 | 如果表定义了主键，就是聚集索引 | — |
| InnoDB 无主键时 | 选第一个非空唯一索引；若都没有，用隐藏的 6 字节 row_id | — |

```
InnoDB 存放结构：

聚集索引 (B+Tree): 主键 id
┌────────────────────────────────┐
│ 非叶子节点                      │
│ [id=10] [id=20] [id=30]       │
└───┬───────┬───────┬───────────┘
    ▼       ▼       ▼
┌──────┐ ┌──────┐ ┌──────┐
│id=10 │→│id=15 │→│id=20 │→ ...  叶子节点存完整行
│name=A│ │name=B│ │name=C│
│age=20│ │age=22│ │age=25│
└──────┘ └──────┘ └──────┘

非聚集索引 (B+Tree): 列 name
┌────────────────────────────────┐
│ 非叶子节点: name 值             │
│ [Alice] [Bob] [Charlie]       │
└───┬───────┬───────┬───────────┘
    ▼       ▼       ▼
┌──────┐ ┌──────┐ ┌──────┐
│Alice │→│Bob   │→│Charlie│→ ...  叶子节点存 name + 主键 id
│id=15 │ │id=10 │ │id=20 │
└──────┘ └──────┘ └──────┘
         │        │
         │ 需要更多字段? → 用 id 回表查聚集索引
         ▼
    回表（再到聚集索引查完整行数据）
```

**回表（Lookup / Bookmark Lookup）**：通过非聚集索引查到主键 id 后，还需要去聚集索引再查一次才能拿到完整行数据。这是非聚集索引带来的额外开销。

**覆盖索引（Covering Index）消除回表**：如果查询的所有字段都在非聚集索引中（索引列 + 主键），则不需要回表。

### 三、最左前缀原则

**对于联合索引 `(a, b, c)`**：

B+Tree 中的数据按 `(a, b, c)` 的顺序排序存储，即先按 a 排序，a 相同时按 b 排序，b 相同时按 c 排序。

```
联合索引 (a, b, c) 叶子节点的数据排布：

(a=1, b=2, c=3)
(a=1, b=2, c=8)
(a=1, b=5, c=1)
(a=2, b=1, c=4)    ← a 变了，a 是第一排序键
(a=2, b=3, c=5)
(a=3, b=1, c=2)
```

**命中与不命中**：

| WHERE 条件 | 是否命中索引 | 原因 |
|------------|------------|------|
| `a = 1` | ✅ 命中 | 匹配最左列 a |
| `a = 1 AND b = 2` | ✅ 命中 | 匹配 a 和 b |
| `a = 1 AND b > 2 AND c = 3` | ⚠️ a, b 命中，c 不命中 | b 是范围查询，c 无法继续匹配 |
| `b = 2` | ❌ 不命中 | 没提供 a，无法定位 |
| `c = 3` | ❌ 不命中 | 跳过了 a 和 b |
| `a > 1 AND b = 2` | ⚠️ a 命中（范围），b 不命中 | a 是范围查询时 b 排好序失效 |
| `a = 1 AND c = 3` | ⚠️ a 命中，c 不命中 | 跳过了 b，c 无序 |
| ORDER BY a,b | ✅ 索引排序 | 天然有序 |
| ORDER BY a DESC,b DESC | ✅ 索引排序 | 反向扫描 |
| ORDER BY b,a | ❌ 需文件排序 | 不符合索引顺序 |

**核心理解**：联合索引按 `(a, b, c)` 的顺序构建，只有**等值查询 `=` 可以用完一列继续用下一列**。一旦遇到**范围查询 `>` `<` `BETWEEN` `LIKE`**，该列还能用但后续列无法继续使用 B+Tree 索引（因为在 b 不同的区间内，c 不再有序）。

### 四、索引失效的常见场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **索引列参与运算** | 运算符/函数破坏了索引 | `WHERE id + 1 = 10` ❌ → 改为 `WHERE id = 9` ✅ |
| **对索引列使用函数** | 函数调用阻止使用索引 | `WHERE DATE(create_time) = '2024-01-01'` ❌ → 改为范围 `WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'` ✅ |
| **隐式类型转换** | 字符串列与数字比较触发隐式转换 | `WHERE phone = 13800138000` ❌（phone 是 varchar）→ `WHERE phone = '13800138000'` ✅ |
| **前导通配符 LIKE** | `%` 开头无法使用索引 | `WHERE name LIKE '%abc'` ❌；`WHERE name LIKE 'abc%'` ✅ |
| **OR 条件** | 一方无索引全表扫描兜底 | `WHERE id = 1 OR name = 'test'`（name 无索引则全表扫描） |
| **不符合左前缀** | 联合索引跳过了左侧列 | 联合索引 (a,b,c)，`WHERE b = 1` ❌ |
| **索引区分度太低** | 优化器认为全表扫描更快 | 性别字段（M/F）建索引意义不大 |
| **不等于/IS NOT NULL** | 可能导致索引失效 | `WHERE status != 'deleted'`（当大部分行不是 deleted 时，优化器可能不走索引） |
| **大范围扫描** | 优化器认为扫描量超过 30% 时可能全表扫 | `WHERE age > 10`（回表成本 > 全表） |

**Explain 解读**：

```sql
EXPLAIN SELECT * FROM users WHERE name = 'Alice';

-- key: 使用的索引
-- type: const > eq_ref > ref > range > index > ALL（越靠左越好）
-- possible_keys: 可能使用的索引
-- rows: 预计扫描行数
-- Extra:
--   Using index     → 覆盖索引，不回表 ✅
--   Using where     → 使用了 WHERE 过滤
--   Using filesort  → 额外排序，需优化 ⚠️
--   Using temporary → 使用临时表，需优化 ⚠️
```

### 五、索引设计的实践建议

1. **选择性高的列优先**：选择性 = 不重复值数 / 总行数，越接近 1 越好
2. **联合索引优于多个单列索引**：`(a,b,c)` 可以覆盖 `WHERE a=? AND b=?` 而多单列索引可能只用一个
3. **考虑 WHERE + ORDER BY + GROUP BY**：让索引覆盖查询的完整流程
4. **避免过多索引**：每个索引都占用空间且在写操作时需要维护
5. **监控慢查询**：用 `slow_query_log` 定位问题，用 `EXPLAIN` 分析

---

## 总结
B+Tree 是数据库索引的主流实现，非叶子节点不存数据使得树更矮，叶子节点链表支持高效范围查询。聚集索引叶子存完整行数据，非聚集索引叶子存索引列 + 主键（可能需回表）。联合索引遵循最左前缀原则——等值查询可以连续匹配多列，范围查询后的列无法继续使用。索引失效常见于对列使用函数、运算、隐式类型转换和前置模糊匹配。
