# 题目：TCP 与 UDP 的区别及 TCP 连接建立与释放

## 问题
请详细对比 TCP 和 UDP 的区别、适用场景，画出 TCP 三次握手和四次挥手的流程图，并说明为什么握手是三次、挥手是四次。

## 考点
- TCP 面向连接 vs UDP 无连接的本质
- TCP 可靠性保障机制（确认应答、超时重传、滑动窗口、拥塞控制）
- 三次握手的必要性（防止历史连接、同步序列号）
- TIME_WAIT 状态的作用（2MSL）
- QUIC 协议对 TCP 的改良

## 解答

### 一、TCP 与 UDP 核心对比

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（确认应答、重传） | 不可靠（尽力交付） |
| 有序性 | 保证顺序 | 不保证顺序 |
| 传输效率 | 较低（有头部开销 + 控制开销） | 高（头部仅 8 字节） |
| 头部大小 | 20-60 字节 | 8 字节 |
| 适用场景 | 文件传输、Web、邮件、远程登录 | 直播、视频通话、DNS、在线游戏 |
| 拥塞控制 | 有（慢启动、拥塞避免、快速重传/恢复） | 无 |
| 流量控制 | 有（滑动窗口） | 无 |
| 广播/多播 | 不支持 | 支持 |

### 二、TCP 三次握手（Three-way Handshake）

```
客户端 CLOSED                     服务端 LISTEN

 1. CLOSED → SYN_SENT
    ──── SYN, seq=x ─────→
                            服务端收到 SYN
                            LISTEN → SYN_RCVD

 2.                    ←──── SYN+ACK, seq=y, ack=x+1 ────

 3. 客户端收到 SYN+ACK
    SYN_SENT → ESTABLISHED
    ──── ACK, seq=x+1, ack=y+1 ─────→      (可以携带数据)
                            服务端收到 ACK
                            SYN_RCVD → ESTABLISHED

双方进入 ESTABLISHED，开始数据传输
```

**为什么需要三次握手，而不是两次？**

1. **防止旧的重复连接请求到达服务端**（RFC 793）：如果客户端发了一个 SYN 由于网络延迟很久才到，服务端以为这是新的连接请求。如果只有两次握手，服务端发送 SYN+ACK 后就认为连接建立，分配资源。但实际上客户端已经放弃了。三次握手让客户端有机会拒绝（不发第三次 ACK）。

2. **同步双方的初始序列号（ISN）**：双方都需要确认对方的初始序列号，确保数据有序传输。客户端需要服务端的 `ack=x+1` 来确认自己的 ISN 被对方收到；服务端也需要客户端的 `ack=y+1` 来确认自己的 ISN 被收到。

3. **双向验证通信能力**：第一次验证客户端发送正常、服务端接收正常；第二次验证服务端发送正常、客户端接收正常；第三次验证客户端的确认能到达服务端。这是建立双向可靠通信的最小次数。

**是否可以携带数据**：
- 第 1、2 次握手不能携带数据
- 第 3 次握手可以携带数据（因为此时客户端已确认双方的收发能力）

### 三、TCP 四次挥手（Four-way Teardown）

```
客户端                              服务端

 1. ESTABLISHED → FIN_WAIT_1
    ──── FIN, seq=u ──────→
                            服务端收到 FIN
                            ESTABLISHED → CLOSE_WAIT

 2.                    ←──── ACK, seq=v, ack=u+1 ────
    客户端收到 ACK
    FIN_WAIT_1 → FIN_WAIT_2

                            (服务端可能还有数据要发...)

                            服务端发完数据
                            CLOSE_WAIT → LAST_ACK

 3.                    ←──── FIN, seq=w, ack=u+1 ────
    客户端收到 FIN
    FIN_WAIT_2 → TIME_WAIT

 4. 客户端等待 2MSL 后
    ──── ACK, seq=u+1, ack=w+1 ──────→
    进入 CLOSED
                            服务端收到 ACK
                            LAST_ACK → CLOSED
```

**为什么挥手是四次，而不是三次？**

TCP 是全双工的，每个方向都需要单独关闭：
- 客户端发 FIN 表示"我没有数据要发了"（关闭客户端→服务端方向）
- 服务端回复 ACK 表示"知道了"
- 但服务端可能还有数据没发完（服务端→客户端方向仍可能活跃）
- 等服务端发完数据后，再发 FIN 表示"我也没有数据要发了"
- 客户端回复 ACK 确认

握手时 SYN 和 ACK 可以合并（SYN+ACK），因为服务端在收到 SYN 后没有更多事情要做，可以立即回复。挥手时服务端收到 FIN 后可能还有数据要发，ACK 和 FIN 不能合并。

**TIME_WAIT 为什么是 2MSL？**

MSL（Maximum Segment Lifetime，最大报文生存时间）通常是 30s 或 60s，2MSL 因此约为 60-120s。

两个目的：
1. **确保最后一个 ACK 能到达服务端**：如果 ACK 丢失，服务端会重传 FIN。客户端在 TIME_WAIT 期间可以重新发送 ACK。2MSL = ACK 最大存活时间 + 服务端重传 FIN 的最大存活时间
2. **让旧连接的所有报文都在网络中消失**：避免旧连接的数据干扰同端口的新连接

**CLOSE_WAIT 过多的排查**：
- 服务端程序收到 FIN 但没有调用 `close()`，即没有发送自己的 FIN
- 常见原因：代码 bug（忘记关闭 socket）、后端处理慢导致连接堆积

### 四、TCP 可靠性保障机制

| 机制 | 说明 |
|------|------|
| **确认应答（ACK）** | 接收方确认收到数据，发送方超时未收到则重传 |
| **超时重传（RTO）** | 动态计算 RTT，用 Karn/Partridge 算法 |
| **滑动窗口** | 流量控制：接收方告知剩余缓冲区大小，发送方据此调节发送速率 |
| **拥塞控制** | 慢启动（指数增长）→ 拥塞避免（线性增长）→ 快重传（3 个重复 ACK）→ 快恢复 |
| **校验和** | 检测数据在传输中是否出错 |

### 五、TCP 状态转换图（关键路径）

```
客户端状态               服务端状态

CLOSED                    LISTEN
  |                         |
  | (主动打开)              | (收到 SYN)
SYN_SENT                  SYN_RCVD
  |                         |
  | (收到 SYN+ACK 发 ACK)  | (收到 ACK)
ESTABLISHED    ← →      ESTABLISHED
  | (主动关闭)              | (收到 FIN)
FIN_WAIT_1                CLOSE_WAIT
  |                         |
  | (收到 ACK)              | (发完数据)
FIN_WAIT_2                LAST_ACK
  |                         |
  | (收到 FIN)              | (收到 ACK)
TIME_WAIT                 CLOSED
  | (2MSL)
CLOSED
```

### 六、适用场景

| 场景 | 推荐协议 | 原因 |
|------|---------|------|
| 网页浏览 (HTTP/HTTPS) | TCP | 需要可靠传输、页面完整性 |
| 文件传输 (FTP/SFTP) | TCP | 不能容忍数据丢失 |
| 电子邮件 (SMTP/POP3) | TCP | 必须可靠 |
| 视频直播 | UDP | 可容忍少量丢包，但要求低延迟 |
| 在线游戏 | UDP | 实时性 > 可靠性 |
| DNS 查询 | UDP (主要) | 单次请求响应，低开销 |
| VoIP 语音通话 | UDP | 实时交互，重传无意义 |
| 数据库连接 | TCP | 数据绝对完整 |

**QUIC（如 HTTP/3 的底层协议）的改进**：
- 基于 UDP，但实现了类似 TCP 的可靠传输
- 0-RTT 握手（减少连接建立时间）
- 无队头阻塞（一个流丢包不影响其他流）
- 连接迁移（切换网络时无需重建连接）

---

## 总结
TCP 面向连接、可靠、有序，通过三次握手建立连接、四次挥手释放连接，适用于对数据完整性要求高的场景。UDP 无连接、不可靠、无序，但传输效率高、延迟低，适用于实时应用。握手的核心是交换并确认双方的初始序列号；TIME_WAIT 状态确保旧报文彻底消失。
