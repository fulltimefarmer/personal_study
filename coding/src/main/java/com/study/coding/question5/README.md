# 题目 5：滑动窗口限流器

## 题目描述

实现一个滑动窗口（sliding-window）限流器，用于控制某个客户端在指定时间窗口内允许的最大请求数。

要求实现：

- `boolean isAllowed(String clientId)` —— 判断来自指定客户端的请求是否允许。如果当前时间窗口内该客户端的请求数未超过上限，返回 `true` 并记录本次请求；否则返回 `false`。
- 限流器应使用**滑动日志（sliding log）算法**：记录每个请求的时间戳，判断时清理窗口外的旧时间戳，再与阈值比较。
- 实现必须是**线程安全**的，支持高并发场景下大量不同客户端同时请求。
- 提供**定期后台清理机制**，移除长时间无流量的客户端数据，防止内存泄漏。

## 示例

```java
RateLimiter limiter = new RateLimiter(3, 10);
// 最大 3 个请求，窗口 10 秒

limiter.isAllowed("client-A");  // true  (1/3)
limiter.isAllowed("client-A");  // true  (2/3)
limiter.isAllowed("client-A");  // true  (3/3)
limiter.isAllowed("client-A");  // false (已达上限)
// ... 等待窗口滑动 (10 秒后) ...
limiter.isAllowed("client-A");  // true  (旧请求已滑出窗口)
```

## 解题思路

### 1. 限流算法对比与选择

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **固定窗口** | 将时间划分为固定窗口，计数 | 实现简单，内存开销小 | 边界突发问题（第 N 秒末尾和第 N+1 秒开头各发满请求） |
| **滑动日志** | 记录每个请求的时间戳 | 精度高，无边界问题 | 内存开销较大（需存储时间戳） |
| **滑动窗口计数器** | 结合固定窗口 + 前一窗口加权 | 内存友好，近似滑动 | 近似值，非精确限流 |
| **令牌桶** | 固定速率生成令牌，请求消耗令牌 | 允许突发，平滑流量 | 需定时补充令牌 |
| **漏桶** | 请求入桶，固定速率漏出处理 | 平滑流量，恒定速率 | 不允许突发 |

**本实现选择滑动日志算法**：精度最高，适合考察数据结构操作和并发控制能力。

### 2. 核心数据结构

```
┌──────────────────────────────────────────────────────────┐
│                     RateLimiter                           │
│                                                           │
│  ConcurrentHashMap<String, ConcurrentLinkedDeque<Long>>   │
│  ┌──────────────┬──────────────────────────────────────┐ │
│  │ clientId     │ Deque<timestamp>                     │ │
│  │ "client-A"   │ [T1, T2, T3]  (按时间递增排列)       │ │
│  │ "client-B"   │ [T4]                                 │ │
│  └──────────────┴──────────────────────────────────────┘ │
│                                                           │
│  ConcurrentHashMap<String, AtomicLong> deniedCounts       │
│  └── 记录每个客户端被拒绝的次数，用于监控               │
│                                                           │
│  ScheduledExecutorService cleanupScheduler                │
│  └── 定期清理无流量的客户端                             │
└──────────────────────────────────────────────────────────┘
```

### 3. isAllowed 方法执行流程

```
                    ┌─────────────┐
                    │  收到请求    │
                    └──────┬──────┘
                           ▼
                  ┌─────────────────┐
                  │ 获取/创建 Deque  │
                  └────────┬────────┘
                           ▼
                  ┌─────────────────┐
                  │ 清理过期时间戳   │  ← 删除 cutoff 之前的所有时间戳
                  │ while head<cutoff│
                  │   pollFirst()    │
                  └────────┬────────┘
                           ▼
              ┌────────────────────────┐
              │  deque.size() < max?   │
              └──────┬──────────┬──────┘
                     ▼ Yes      ▼ No
            ┌─────────────┐  ┌──────────────┐
            │ 记录时间戳    │  │ 拒绝，计数+1   │
            │ 返回 true    │  │ 返回 false    │
            └─────────────┘  └──────────────┘
```

### 4. 并发安全设计

| 策略 | 实现 | 原因 |
|------|------|------|
| 整体数据结构 | `ConcurrentHashMap` | 不同客户端无锁竞争 |
| 单客户端时间戳 | `ConcurrentLinkedDeque` + `synchronized(deque)` | 仅对同一客户端的操作串行化，精确控制 |
| 拒绝计数 | `AtomicLong` | 无锁计数 |
| 清理操作 | 单线程 `ScheduledExecutorService` | 避免并发清理复杂性 |

**细粒度锁设计**：每个客户端独立加锁，不同客户端之间完全无锁竞争，最大程度提高并发性能。

### 5. 定期清理机制

```
cleanupStaleClients() 执行流程：
1. 遍历所有客户端的 Deque。
2. 对每个 Deque 加锁，清理过期时间戳。
3. 如果 Deque 为空（说明该客户端在当前窗口内无活跃请求）：
   → 从 clientTimestamps 中移除该客户端
   → 从 deniedCounts 中移除该客户端
```

清理间隔建议设为窗口长度的 1~2 倍，既避免过于频繁的清理开销，又不会积累过多僵尸数据。

### 6. 可观测性

通过 `getStats(clientId)` 方法暴露每个客户端的统计数据：
- `currentWindowCount`：当前窗口内的请求数
- `totalDenied`：累计被拒绝请求数

这在生产环境中对接监控系统（Prometheus/Micrometer）至关重要。

### 7. 复杂度分析

- **时间复杂度**：
  - `isAllowed`：均摊 O(1)（每个时间戳只入队和出队一次，即使单次可能遍历多个过期条目）。
  - `cleanup`：O(C)，C 为活跃客户端数量。
- **空间复杂度**：O(R)，R 为当前窗口内所有客户端的活跃请求数总和。

## 考察维度

- **系统设计思维**：限流算法的选择与 trade-off 分析。
- **并发编程**：细粒度锁、ConcurrentHashMap、无锁数据结构的使用。
- **生产工程实践**：可配置参数、监控暴露、定期清理、优雅关闭。
- **代码质量**：清晰的抽象层（不同限流算法可扩展为接口）、完善的 Javadoc。
