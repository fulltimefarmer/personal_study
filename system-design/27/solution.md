# 设计一致性哈希 (Design Consistent Hashing Implementation)

## 题目

设计并实现一致性哈希算法，用于分布式缓存/存储系统中的数据分片和负载均衡。深入分析一致性哈希的原理、虚拟节点、数据迁移和实际工程应用。

## 需求澄清

### 功能性需求

1. **数据分布**: 将 key 均匀分布到 N 个物理节点上
2. **动态扩缩容**: 添加/移除节点时最小化数据迁移
3. **虚拟节点**: 支持虚拟节点解决负载不均问题
4. **权重支持**: 不同节点可以有不同权重(处理能力)
5. **范围查询**: 支持查询 key 对应的节点
6. **节点健康管理**: 节点故障检测和自动摘除
7. **分区感知 (Rack Awareness)**: 避免数据副本分布在同一机架

### 非功能性需求

- **均匀性**: 数据分布标准差 < 5%
- **低迁移率**: 添加1个节点，最多 1/N 的数据需要迁移
- **低延迟**: key→node 映射 < 1μs
- **内存高效**: 百万级 key 场景下元数据开销小

### 容量估算

```
假设集群规模:
- 物理节点: 1000台
- 每节点虚拟节点: 150个
- 总虚拟节点: 150,000个
- 每个key(如缓存): 平均 1KB

迁移量估算:
- 新增1台物理节点(1000→1001):
  - 理论最小迁移 = 1/1001 ≈ 0.1% 数据
  - 实际迁移 = 1/1001 × 150 虚拟节点重分布 ≈ 需要迁移的数据比例
  - 如果总数据 100TB → 新增节点迁移约 100GB
- 节点故障:
  - 故障节点的数据需要重新分配到其他节点
  - 1台节点的数据(100GB) → 分散到剩余999台
```

## API设计

```java
// 一致性哈希的核心接口设计

public interface ConsistentHash<K, N> {
    
    /**
     * 添加一个物理节点
     * @param node 节点标识
     * @param weight 权重 (可选, 默认1)
     */
    void addNode(N node, int weight);
    
    /**
     * 移除一个物理节点
     * @param node 节点标识
     */
    void removeNode(N node);
    
    /**
     * 获取 key 对应的节点
     * @param key 数据的key
     * @return 目标节点
     */
    N getNode(K key);
    
    /**
     * 获取 key 对应的 N 个节点 (用于副本)
     * @param key 数据的key
     * @param count 需要的节点数
     * @return 节点列表 (按优先级排序)
     */
    List<N> getNodes(K key, int count);
    
    /**
     * 获取所有节点
     */
    Set<N> getAllNodes();
    
    /**
     * 获取节点当前的负载统计
     */
    Map<N, Integer> getLoadDistribution(int sampleKeys);
}

// 一致性哈希的实现
public class ConsistentHashRing<K, N> implements ConsistentHash<K, N> {
    
    // 核心数据结构: 有序Map (如 TreeMap) 存储虚拟节点
    private final TreeMap<Integer, N> ring = new TreeMap<>();
    
    // 物理节点 → 虚拟节点数量映射
    private final Map<N, Integer> nodeVirtualCount = new HashMap<>();
    
    // 默认每个物理节点的虚拟节点数
    private static final int DEFAULT_VIRTUAL_NODES = 150;
    
    // 哈希函数
    private final HashFunction hashFunction;
    
    /**
     * 构造时初始化哈希函数
     * 使用 MurmurHash3 或 MD5 提取部分位
     */
    public ConsistentHashRing(HashFunction hashFunction) {
        this.hashFunction = hashFunction;
    }
    
    @Override
    public void addNode(N node, int weight) {
        int virtualNodes = DEFAULT_VIRTUAL_NODES * weight;
        nodeVirtualCount.put(node, virtualNodes);
        
        for (int i = 0; i < virtualNodes; i++) {
            // 虚拟节点命名: node.toString() + "#" + i
            String virtualNodeKey = node.toString() + "#" + i;
            int hash = hashFunction.hash(virtualNodeKey);
            ring.put(hash, node);
        }
    }
    
    @Override
    public void removeNode(N node) {
        int virtualNodes = nodeVirtualCount.getOrDefault(node, 0);
        for (int i = 0; i < virtualNodes; i++) {
            String virtualNodeKey = node.toString() + "#" + i;
            int hash = hashFunction.hash(virtualNodeKey);
            ring.remove(hash);
        }
        nodeVirtualCount.remove(node);
    }
    
    @Override
    public N getNode(K key) {
        if (ring.isEmpty()) {
            return null;
        }
        int hash = hashFunction.hash(key.toString());
        
        // 顺时针查找第一个 >= hash 的虚拟节点
        Map.Entry<Integer, N> entry = ring.ceilingEntry(hash);
        if (entry == null) {
            // 超过最大值, 回到环的起点
            entry = ring.firstEntry();
        }
        return entry.getValue();
    }
    
    @Override
    public List<N> getNodes(K key, int count) {
        List<N> result = new ArrayList<>();
        Set<N> seen = new HashSet<>();
        
        int hash = hashFunction.hash(key.toString());
        Map.Entry<Integer, N> entry = ring.ceilingEntry(hash);
        if (entry == null) {
            entry = ring.firstEntry();
        }
        
        // 从起始位置顺时针遍历, 收集 count 个不同物理节点
        SortedMap<Integer, N> tailMap = ring.tailMap(entry.getKey());
        Iterator<Map.Entry<Integer, N>> it = tailMap.entrySet().iterator();
        
        while (result.size() < count) {
            if (!it.hasNext()) {
                // 绕回环的起点
                it = ring.entrySet().iterator();
            }
            N node = it.next().getValue();
            if (seen.add(node)) {
                result.add(node);
            }
        }
        return result;
    }
}

### 1. 哈希函数的选择

```
┌────────────────────────────────────────────────────────────────┐
│                    哈希函数对比                                  │
│                                                                │
│  要求:                                                          │
│  - 均匀分布 (Uniform Distribution)                              │
│  - 低碰撞率                                                     │
│  - 计算速度快                                                    │
│                                                                │
│  候选函数:                                                      │
│                                                                │
│  1. MD5 (128-bit)                                              │
│  ─────────────────────────────                                  │
│  优点: 分布均匀, 碰撞率极低                                      │
│  缺点: 计算相对慢 (~3.5 GB/s per core)                          │

│                                                                │

│  ─────────────────────────────                                  │
│  优点: 速度快 (~6 GB/s per core), 分布均匀                      │
│  缺点: 非加密安全 (此处不影响)                                   │

│                                                                │
│  3. FNV (Fowler-Noll-Vo)                                       │
│  ─────────────────────────────                                  │
│  优点: 简单, 快速                                               │

│  ─────────────────────────────                                  │

│                                                                │
│  ┌──────────────────────────────────────────────────────┐     │

### 4. 一致性哈希的数学分析

```
┌────────────────────────────────────────────────────────────────┐
│                    一致性哈希的数学性质                           │
│                                                                │
│  负载分布 (Load Distribution):                                   │
│  ────────────────────────────────────────────────               │
│                                                                │
│  设:  K = key的数量, N = 物理节点数, V = 每节点虚拟节点数      │
│                                                                │
│  每个虚拟节点落在环上的位置是均匀随机的                            │
│  环被分成 N×V 个区间, 每个区间期望大小相同                       │
│                                                                │
│  每个物理节点的负载期望值: K/N                                    │
│  负载标准差:                                                    │
│    σ ≈ sqrt(K / (N×V))  ×  (1/N)                               │
│       = sqrt(K) / (N × sqrt(V))                                │
│                                                                │
│  示例: K=1,000,000, N=10, V=150                                │
│    σ ≈ sqrt(1,000,000) / (10 × sqrt(150))                      │
│      = 1000 / (10 × 12.25)                                     │
│      = 1000 / 122.5                                            │
│      ≈ 8.16                                                    │
│                                                                │
│  期望每个节点: 100,000 keys                                      │
│  变异系数 (CV) = 8.16 / 100,000 = 0.008%                       │
│  → 负载非常均匀!                                                │
│                                                                │
│  迁移率 (Migration Ratio):                                      │
│  ────────────────────────────────────────────────               │
│  增加1个节点后:                                                  │
│    需要迁移比例 = 1 / (N+1) × 100%                              │
│                                                                 │
│  N=10 → 迁移 = 1/11 ≈ 9.1%                                     │
│  N=100 → 迁移 = 1/101 ≈ 0.99%                                  │
│  N=1000 → 迁移 = 1/1001 ≈ 0.1%                                 │
│                                                                 │
│  与取模哈希 (Modulo) 的对比:                                     │
│  ┌───────────────────────────────────────────────────────┐    │
│  │                        │  Modulo    │ Consistent Hash │    │
│  │  ──────────────────────┼────────────┼─────────────────│    │
│  │  增加节点迁移比例       │  90% (N=10→11)│  9%            │    │
│  │  增加节点迁移比例       │  99% (N=100→101)│ 1%           │    │
│  │  节点down影响          │  100% 重分布 │  仅该节点数据    │    │
│  │  负载均衡              │  完美       │  近似均匀(V足够) │    │
│  │  实现复杂度            │  极简单     │  中等           │    │
│  └───────────────────────────────────────────────────────┘    │
└────────────────────────────────────────────────────────────────┘

│  │  int jumpConsistentHash(long key, int numBuckets) {       │  │
│  │      long b = -1, j = 0;                                  │  │
│  │      while (j < numBuckets) {                              │  │
│  │          b = j;                                            │  │
│  │          key = key * 2862933555777941757L + 1;            │  │
│  │          j = (long)((b + 1) * (1L << 31) /                │  │
│  │               ((key >> 33) + 1));                         │  │
│  │      }                                                     │  │
│  │      return (int)b;                                        │  │
│  │  }                                                         │  │
│  │                                                          │  │
│  │  适用场景: 数据存储分片, 分桶数量固定或只增不减             │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  变体2: Multi-Probe Consistent Hashing                          │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  用于 Google 的负载均衡 (Maglev / Envoy)                  │  │
│  │  在原始一致性哈希基础上:                                    │  │
│  │  - 对每个 key 计算多个哈希位置                              │  │
│  │  - 选择第一个可用的节点                                     │  │
│  │  - 优点: 故障转移时最小化连接中断                           │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  变体3: Rendezvous Hashing (最高随机权重哈希)                    │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  hash(key, node) → weight                                  │  │
│  │  选择 weight 最高的节点                                    │  │
│  │                                                          │  │
│  │  优点: 负载最均衡, 删除节点时只重分配该节点数据             │  │
│  │  缺点: O(N) 复杂度 (需要与所有节点比较权重)                 │  │
│  │  适用: 节点数小的场景 (< 100)                              │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 6. 分片感知与副本策略

```
┌────────────────────────────────────────────────────────────────┐
│             副本放置策略 (Replica Placement)                     │
│                                                                │
│  要求: 数据的N个副本必须放在不同的物理节点/机架/数据中心          │
│                                                                │
│  策略: 顺时针连续遍历, 跳过不符合条件的节点                      │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  Ring: A1 B1 C1 D1 A2 B2 C2 D2 A3 ...                   │  │
│  │                                                          │  │
│  │  Key的hash落在 A2 →                                       │  │
│  │    Replica 0: A (顺时针下一个是B1? 不对, 是A2→A)           │  │
│  │    Replica 1: 继续顺时针 → B1 → B                          │  │
│  │    Replica 2: 继续顺时针 → C1 → C                          │  │
│  │                                                          │  │
│  │  Rack-aware:                                              │  │
│  │    Replica 1: 跳过与 A 同机架的节点, 选下一个不同机架的     │  │
│  │    Replica 2: 跳过与 A, B 同机架的, 选不同机架的           │  │
│  │                                                          │  │
│  │  伪代码:                                                  │  │
│  │  nodes = ring.iterate_from(hash)                          │  │
│  │  replicas = []                                            │  │
│  │  for node, rack in nodes:                                 │  │
│  │      if node not in replicas                              │  │
│  │         and rack not in seen_racks:                       │  │
│  │          replicas.add(node)                                │  │
│  │          seen_racks.add(rack)                              │  │
│  │      if len(replicas) == desired: break                   │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 7. 实际应用: 分布式缓存中的一致性哈希

```
┌────────────────────────────────────────────────────────────────┐
│           一致性哈希在分布式缓存中的应用                          │
│                                                                │
│  Memcached / Redis Cluster 的一致性哈希客户端:                  │
│                                                                │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  客户端 (App Server)                                      │  │
│  │  ┌──────────────────────────────────────────────────┐   │  │
│  │  │ ConsistentHashRing (本地内存)                     │   │  │
│  │  │                                                  │   │  │
│  │  │  GET("user:1001")                                │   │  │
│  │  │    → hash("user:1001") = 0x8F2A...                │   │  │
│  │  │    → ring.getNode(0x8F2A...) → "cache-03"        │   │  │
│  │  │    → TCP connect to cache-03:11211                │   │  │
│  │  └──────────────────────────────────────────────────┘   │  │
│  │                                                          │  │
│  │  优点: 无中心化, 客户端自主路由, 单点故障不影响             │  │
│  │  缺点: 所有客户端必须同步节点变更信息                      │  │
│  │                                                          │  │
│  │  节点变更同步方案:                                        │  │
│  │  1. ZooKeeper/Etcd: 监听 /cache/nodes 节点变更事件       │  │
│  │  2. Gossip 协议: 节点间互相通知 (如Cassandra)             │  │
│  │  3. 配置中心: 定期拉取最新节点列表                        │  │
│  │  4. DNS: 更新DNS记录, 客户端定期解析                      │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  数据一致性保证 (读写流程):                                      │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  写流程:                                                  │  │
│  │  1. 计算 key 的哈希值                                     │  │
│  │  2. 找 N 个副本节点                                       │  │
│  │  3. 并发写入 (或按序写), 等待 W 个成功确认                │  │
│  │                                                          │  │
│  │  读流程:                                                  │  │
│  │  1. 计算 key 的哈希值                                     │  │
│  │  2. 找 N 个副本节点                                       │  │
│  │  3. 并发读取, 等待 R 个返回                               │  │
│  │  4. 合并结果, 修复不一致的副本 (Read Repair)               │  │
│  │                                                          │  │
│  │  Quorum: W + R > N (如 N=3, W=2, R=2 → 强一致性)         │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 节点故障处理

```
┌──────────────────────────────────────────────────────────────┐
│                节点故障处理流程                                │
│                                                              │
│  检测:                                                        │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ - 心跳检测 (每秒)                                      │   │
│  │ - 连续3次失败 → 标记为 down                           │   │
│  │ - 避免误判: 使用 Phi Accrual Failure Detector         │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  处理:                                                        │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 1. 从 ring 中移除故障节点的所有虚拟节点                 │   │
│  │ 2. 故障节点的数据 → 顺时针下一个节点负责                │   │
│  │ 3. 通知所有客户端更新 ring                              │   │
│  │ 4. 后续对该key的请求自动路由到新节点                     │   │
│  │ 5. 如果故障节点恢复:                                     │   │
│  │    - 需要数据同步后再加入 ring                           │   │
│  │    - 或者直接作为新节点加入 (数据重分布)                  │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  安全边际:                                                    │
│  - 虚拟节点保证故障节点的数据均匀分散到其他节点                │
│  - 不会造成单个节点负载激增                                   │
└──────────────────────────────────────────────────────────────┘
```

## 总结

| 维度 | 技术选型 | 理由 |
|------|---------|------|
| 核心数据结构 | TreeMap / 有序列表 | O(log N) 查找环形位置 |
| 哈希算法 | MurmurHash3 | 速度快 + 分布均匀 |
| 虚拟节点数 | 100-150/节点 | 平衡均匀性和内存开销 |
| 数据迁移 | 惰性迁移(Hybrid) | 最小化影响在线服务 |
| 副本策略 | 顺时针连续遍历 + Rack-aware | 满足故障域隔离 |
| 节点变更通知 | ZooKeeper/Etcd/Gossip | 实时 + 可靠 |
| 一致性 | Quorum (R+W > N) | 读写可调 |

核心设计要点:
1. **虚拟节点是均匀分布的关键**: 没有虚拟节点, 一致性哈希只是"比较均匀", 有虚拟节点后才真正均匀
2. **虚拟节点数量需要权衡**: 太少不均匀, 太多浪费内存(但还好,1000台×150≈15万个点, 约1.2MB)
3. **数据迁移最小化**: 新增/移除1台节点 ≈ 1/N 数据迁移, 远优于取模哈希的 ~100%
4. **树结构是天然选择**: TreeMap/TreeSet 的 ceilingEntry 完美实现顺时针查找
5. **考虑异构节点**: 通过权重 × 虚拟节点数, 让强节点承担更多数据
6. **一致性哈希≠最终方案**: 需要在一致性哈希之上叠加副本策略、故障检测、数据修复
