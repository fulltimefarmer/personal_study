# 设计热门话题/Top K系统 (Design Top K / Trending Topics System)

## 题目

设计一个类似 Twitter Trending Topics 的热门话题/Top K 系统，实时追踪和展示当前最热门的话题、搜索词或内容。

## 需求澄清

### 功能性需求

1. **实时热门话题**: 按分钟/小时级别展示Top K个最热话题
2. **时间窗口支持**: 最近5分钟、1小时、24小时、7天热门
3. **衰减机制**: 旧数据热度随时间衰减(decay)
4. **话题聚合**: 相似话题合并(e.g., "#WorldCup", "#WorldCupFinal", "World Cup")
5. **地理位置**: 支持按国家/城市的热门话题
6. **屏蔽与审核**: 人工屏蔽不当话题，防止刷榜
7. **趋势检测**: 不仅看绝对计数，也看增长速率(velocity)
8. **话题详情**: 点击热门话题查看相关内容和讨论量

### 非功能性需求

- **低延迟**: 话题更新 < 1分钟
- **高吞吐**: 支持每秒百万级事件(Tweet、搜索、点击)
- **可扩展**: 支持亿级话题基数
- **准确性**: Top K 排名与全量计算结果误差 < 5%(可用近似算法)
- **高可用**: 99.9%

### 容量估算

```
假设 (Twitter规模):
- 日均推文: 5亿条
- 日均搜索: 20亿次
- 话题提取: 每条推文提取1-3个话题
- 活跃话题数: ~100万/天
- Top K 展示: K=50

事件量:
- 推文: 5亿 / 86400 ≈ 5,800 条/秒
- 峰值: 5,800 × 10 = 58,000 条/秒
- 话题事件: 58,000 × 2 = 116,000 topic events/秒
- 搜索事件: 20亿 / 86400 ≈ 23,000 次/秒

存储估算:
- 每个时间窗口的计数:
  - 1分钟窗口: 100万活跃话题 × 4B ≈ 4 MB
  - 1小时窗口: 同上
  - 每个topic需要维护多个窗口的计数
- 话题元数据: 100万 × 500B ≈ 500 MB
- 聚合表 (Redis/Cassandra): ~10 GB

Top K查询QPS: ~10,000 (用户刷新页面 + API调用)
```

## API设计

```protobuf
// ============ 话题数据上报 API ============
// POST /api/v1/topics/events (批量)
message TopicEventBatch {
  repeated TopicEvent events = 1;
  string source = 2;                   // "tweet", "search", "click", "hashtag"
  int64 batch_timestamp_ms = 3;
}

message TopicEvent {
  string topic = 1;                    // "#WorldCup" or "World Cup"
  string topic_id = 2;                 // 规范化后的话题ID
  TopicEventType type = 3;            // CREATE, SEARCH, VIEW, SHARE, LIKE
  int64 event_timestamp_ms = 4;
  int64 user_id = 5;                   // 可选, 用于去重
  string region = 6;                   // 可选, 如 "US", "CN", "CA-ON"
  string language = 7;                 // 可选
  double weight = 8 [default = 1.0];   // 事件权重 (share=3, like=2, view=1)
  map<string, string> metadata = 9;
}

enum TopicEventType {
  CREATE = 0;                          // 创建/提及话题
  SEARCH = 1;                          // 搜索
  VIEW = 2;                            // 浏览
  SHARE = 3;                           // 分享 (高权重)
  LIKE = 4;                            // 点赞 (中权重)
  CLICK = 5;                           // 点击
}

// ============ 热门话题查询 API ============
// GET /api/v1/trending?window=1h&region=US&limit=50&category=all

message TrendingRequest {
  string window = 1;                   // "5m", "1h", "24h", "7d"
  string region = 2;                   // "US", "CN", "global"
  string language = 3;                 // "en", "zh"
  string category = 4;                 // "news", "sports", "entertainment", "all"
  int32 limit = 5 [default = 50];
}

message TrendingResponse {
  repeated TrendingTopic topics = 1;
  int64 generated_at_ms = 2;
  string window = 3;
  string region = 4;
}

message TrendingTopic {
  string topic = 1;
  string topic_id = 2;
  int64 rank = 3;
  double score = 4;                    // 热度分数
  int64 count = 5;                     // 绝对计数
  double velocity = 6;                 // 增长速度 (events per minute)
  string trend_direction = 7;          // "up", "down", "stable", "new"
  int64 rank_change = 8;               // 排名变化 (+上升, -下降)
  string description = 9;              // 简短描述
  int64 total_posts = 10;              // 相关帖子总数
}

// ============ 话题趋势查询 API ============
// GET /api/v1/topics/{topic_id}/trend?window=24h&granularity=1h

message TopicTrendResponse {
  string topic_id = 1;
  string window = 2;
  string granularity = 3;              // "1m", "5m", "1h", "1d"
  repeated TrendPoint points = 4;
}

message TrendPoint {
  int64 timestamp_ms = 1;
  double score = 2;
  int64 count = 3;
}
```

# 使用 Redis Sorted Set, key = 窗口标识, member = topic_id, score = count

# 1分钟窗口计数器 (每分钟一个key)

# 5分钟窗口 (流处理预聚合)
# Key: trending:5m:{timestamp}
ZINCRBY trending:5m:20240101_1200 topic_12345 5

# 1小时窗口

ZINCRBY trending:1h:20240101_1200 topic_12345 300

# 获取最近1小时Top 50
# 计算需要合并的60个1分钟窗口
# 方案A: ZUNIONSTORE 合并60个key (量大时慢)
# 方案B: 直接查询预聚合的1小时窗口

ZREVRANGE trending:1h:20240101_1200 0 49 WITHSCORES

# ============ 指数衰减计数 (Exponential Decay) ============

# Redis Sorted Set 实现衰减替代方案:
# 使用固定时间槽 + 查询时计算加权分数

    topic_id VARCHAR(64) PRIMARY KEY,
    normalized_name VARCHAR(500) NOT NULL,   -- 规范化话题名

    INDEX idx_topic (topic_id),
    INDEX idx_alias (alias)
);

    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    region VARCHAR(10) DEFAULT 'global',
    rank INT NOT NULL,
    score DOUBLE NOT NULL,
    count BIGINT NOT NULL,
    snapshot_time TIMESTAMP NOT NULL,
    INDEX idx_time_topic (snapshot_time, topic_id),
    INDEX idx_window_rank (window_type, region, rank, snapshot_time)
);

## 核心深入

### 1. 热度分数计算

```
┌────────────────────────────────────────────────────────────────┐
│                热度分数 (Trending Score) 计算                    │
│                                                                │
│  基础公式 (修改版 Hacker News / Reddit 算法):                   │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│                                                                │
│  简单版 (仅计数):                                               │
│  score = count_in_window                                       │
│  问题: 不看增长速度, 老话题永远在榜上                             │
│                                                                │
│  改进版 (计数 + 速度):                                          │
│                                                                │
│  score = count × velocity                                      │
│  velocity = (count_current_window - count_prev_window)         │
│            / window_size_seconds                                │
│                                                                │
│  更优版 (指数衰减 + 权重 + 增长速度):                           │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  score = Σ(weight_i × e^(-λ × (t_now - t_i)))            │  │
│  │                                                          │  │
│  │  其中:                                                    │  │
│  │    weight_i = event_type_weight (share=3, like=2, view=1)│  │
│  │    λ = 衰减常数 = ln(2) / half_life                      │  │
│  │    half_life = 30分钟 (最热话题) / 6小时 (一般话题)        │  │
│  │    t_i = 事件发生时间                                     │  │
│  │                                                          │  │
│  │  例子:                                                    │  │
│  │    share事件, 20分钟前: weight=3 × e^(-0.023 × 20) = 1.9 │  │
│  │    view事件, 5分钟前:   weight=1 × e^(-0.023 × 5) = 0.89 │  │
│  │    score = 1.9 + 0.89 = 2.79                             │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  实际生产环境适用的简化方案:                                      │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  使用分层时间槽 (Bucketed Time Slots):                     │  │
│  │                                                          │  │
│  │  slot_0: 最近1分钟                                        │  │
│  │  slot_1: 1-2分钟前                                        │  │
│  │  slot_2: 2-3分钟前                                        │  │
│  │  ...                                                      │  │
│  │  slot_59: 59-60分钟前                                     │  │
│  │                                                          │  │
│  │  score = Σ(bucket_count[i] × e^(-λ × i))                │  │
│  │                                                          │  │
│  │  Redis实现: 为每个topic维护一个 固定大小的 sorted set      │  │
│  │  Member(分钟时间戳) → Score(该分钟计数)                    │  │
│  │  查询时按衰减系数加权求和                                  │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 2. Top K 近似算法: Count-Min Sketch

```
┌────────────────────────────────────────────────────────────────┐
│            Count-Min Sketch: 大数据量下的近似计数               │
│                                                                │
│  问题: 所有话题计数都在内存中, 话题基数太大                      │
│  解决: Count-Min Sketch 概率数据结构                            │
│                                                                │
│  原理:                                                         │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  Count-Min Sketch 是一个二维数组:                          │  │
│  │  width = w, depth = d                                     │  │
│  │                                                          │  │
│  │  sketch[d][w] = 0 (初始化为0)                              │  │
│  │                                                          │  │
│  │  增加计数:                                                 │  │
│  │  for i in 0..d-1:                                        │  │
│  │      j = hash_i(topic) % w                                │  │
│  │      sketch[i][j] += 1                                    │  │
│  │                                                          │  │
│  │  查询计数: (返回上界估计值)                                 │  │
│  │  min(sketch[0][hash_0%w], sketch[1][hash_1%w], ...,      │  │
│  │       sketch[d-1][hash_d-1%w])                           │  │
│  │                                                          │  │
│  │  示例: w=1000, d=5                                         │  │
│  │  Topic "WorldCup":                                        │  │
│  │    hash_0 → 342  count[0][342] = 127                     │  │
│  │    hash_1 → 889  count[1][889] = 115                     │  │
│  │    hash_2 → 501  count[2][501] = 112                     │  │
│  │    hash_3 → 234  count[3][234] = 130                     │  │
│  │    hash_4 → 776  count[4][776] = 108                     │  │
│  │    estimate = min(127, 115, 112, 130, 108) = 108         │  │
│  │    实际值 = 100 (误差 < 8%)                                │  │
│  │                                                          │  │
│  │  误差界:                                                   │  │
│  │    count ≤ estimate ≤ count + ε × N                       │  │
│  │    其中 ε = e/w (w增大误差减小)                             │  │
│  │    误差概率 δ = e^(-d) (d增大成功率提高)                    │  │
│  │                                                          │  │
│  │  内存: w × d × 4 bytes                                     │  │
│  │  例如 w=10000, d=5 → 200 KB (可以存几十万个话题!)         │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  使用 Count-Min Sketch 做 Top K:                                │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  1. 维护一个 Count-Min Sketch 作为快速计数器               │  │
│  │  2. 同时维护一个大小受限的 exact counter map (top 1000)   │  │
│  │  3. 如果 topic 在 exact map 中 → 精确计数                  │  │
│  │  4. 如果 topic 不在 exact map 中 → 用 CMS 估计             │  │
│  │  5. 如果 CMS 估计值 > exact map 的第1000名 → 提升到exact   │  │
│  │                                                          │  │
│  │  改进: HeavyKeeper / Lossy Counting / SpaceSaving        │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 3. SpaceSaving 算法 (精确 Top K)

```
┌────────────────────────────────────────────────────────────────┐
│              SpaceSaving 算法: Top K 精确近似                   │
│                                                                │
│  原理: 维护一个大小为 K 的监控列表                               │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│                                                                │
│  Java 伪代码实现:                                              │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  class SpaceSavingTopK {                                  │  │
│  │      static class Counter {                               │  │
│  │          String item;                                     │  │
│  │          long count;                                      │  │
│  │          long error;  // 最大误差上界                      │  │
│  │      }                                                    │  │
│  │                                                          │  │
│  │      Counter[] monitored = new Counter[K];                │  │
│  │      int size = 0;                                        │  │
│  │                                                          │  │
│  │      void add(String item) {                              │  │
│  │          // 1. 如果item已经在监控列表中                     │  │
│  │          int idx = find(item);                             │  │
│  │          if (idx != -1) {                                  │  │
│  │              monitored[idx].count++;                       │  │
│  │              return;                                       │  │
│  │          }                                                 │  │
│  │                                                          │  │
│  │          // 2. 如果监控列表未满                             │  │
│  │          if (size < K) {                                   │  │
│  │              monitored[size] = new Counter(item, 1, 0);    │  │
│  │              size++;                                       │  │
│  │              return;                                       │  │
│  │          }                                                 │  │
│  │                                                          │  │
│  │          // 3. 替换计数最小的                               │  │
│  │          int minIdx = findMinIndex();                      │  │
│  │          long minCount = monitored[minIdx].count;          │  │
│  │          monitored[minIdx] = new Counter(                   │  │
│  │              item, minCount + 1, minCount);                │  │
│  │      }                                                     │  │
│  │  }                                                         │  │
│  │                                                          │  │
│  │  特性:                                                     │  │
│  │  - 真正的count ≤ 返回的count ≤ 真正的count + error        │  │
│  │  - 内存固定: O(K)                                          │  │
│  │  - 每操作 O(1) (使用min-heap维护最小计数)                   │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  SpaceSaving vs Count-Min Sketch:                               │
│  ┌────────────────────┬────────────────┬───────────────┐       │
│  │ 维度                │ SpaceSaving    │ Count-Min     │       │
│  ├────────────────────┼────────────────┼───────────────┤       │
│  │ 追踪项目数          │ K (数百)       │ 无限制        │       │
│  │ Top K精确度         │ 高 (有误差界)  │ 中 (需额外获取)│       │
│  │ 单点查询            │ O(1)           │ O(d)          │       │
│  │ 内存                │ O(K)           │ O(w×d)        │       │
│  │ 适用场景            │ Top K查询      │ 任意item计数   │       │
│  └────────────────────┴────────────────┴───────────────┘       │
└────────────────────────────────────────────────────────────────┘
```

### 4. 趋势检测 (Trend Detection)

```
┌────────────────────────────────────────────────────────────────┐
│                    趋势检测算法                                  │
│                                                                │
│  目的: 区分"一直很热"和"突然爆火"的话题                          │
│                                                                │
│  方法1: 两个窗口对比                                            │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  trend_score = count_current_window /                    │  │
│  │                (count_prev_window + epsilon)              │  │
│  │                                                          │  │
│  │  示例:                                                    │  │
│  │  - 平常每分钟 100 条, 当前每分钟 500 条                      │  │
│  │    → trend_score = 500/101 ≈ 4.95 → 趋势上升!             │  │
│  │  - 平常每分钟 1000 条, 当前每分钟 1100 条                    │  │
│  │    → trend_score = 1100/1001 ≈ 1.1 → 稳定                  │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  方法2: 时间序列异常检测                                         │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  使用历史数据 (过去7天同一时刻的计数分布):                  │  │
│  │                                                          │  │
│  │  mean = avg(过去7天同一时间点的count)                      │  │
│  │  stddev = std(过去7天同一时间点的count)                     │  │
│  │                                                          │  │
│  │  z_score = (current_count - mean) / stddev               │  │
│  │                                                          │  │
│  │  如果 z_score > 3 → 显著异常 → 标记为趋势上升              │  │
│  │  如果 z_score > 5 → 极端异常 → 标记为突发事件               │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  方法3: 移动平均 (用于趋势方向判断)                              │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │  SMA(简单移动平均) = (c1 + c2 + ... + cn) / n            │  │
│  │  EMA(指数移动平均) = α × c + (1-α) × EMA_prev            │  │
│  │                                                          │  │
│  │  趋势方向:                                                 │  │
│  │  "up" → newest_count > SMA × 1.2                         │  │
│  │  "down" → newest_count < SMA × 0.8                       │  │
│  │  "stable" → otherwise                                    │  │
│  │  "new" → topic 之前不在Top 2000中，突然进入Top 50           │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 5. 大规模下的 Top K 查询优化

```
┌────────────────────────────────────────────────────────────────┐
│           大规模 Top K 查询的工程优化                             │
│                                                                │
│  问题: 从百万话题中随时查询 Top 50                               │
│                                                                │
│  方案一: 预计算 Top K (推荐)                                     │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  使用 Redis Sorted Set + Flink 定时任务:                  │  │
│  │                                                          │  │
│  │  Flink 每分钟执行:                                        │  │
│  │  1. 计算过去1小时的聚合计数                                │  │
│  │  2. 排序取出 Top 1000                                     │  │
│  │  3. 写入 Redis:                                          │  │
│  │     ZADD trending:computed:1h:<now> topic_id score       │  │
│  │  4. 用户查询直接 ZREVRANGE, 无需实时计算                   │  │
│  │                                                          │  │
│  │  优点: 查询 O(1)                                           │  │
│  │  缺点: 有1分钟延迟                                         │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  方案二: 分片 + 并行 + 合并 (适合实时性要求高的场景)             │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  1. 将话题按 hash(topic_id) % N 分到 N shard             │  │
│  │  2. 每个 shard 在 Redis 中维护一个 Sorted Set:            │  │
│  │     trending:shard:{i}:{window}                           │  │
│  │  3. 查询时并发请求所有 shard 的 Top K                      │  │
│  │  4. 合并每个 shard 的 Top K → 全局 Top K                  │  │
│  │                                                          │  │
│  │  示例: N=32, K=50                                         │  │
│  │  并行查32个 shard 的 Top 50 → 1600个候选                   │  │
│  │  排序取 Top 50 → 返回                                     │  │
│  │                                                          │  │
│  │  复杂度: O(N) 网络请求 + O(NK log NK) 排序                 │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  方案三: 时间窗口轮转 (Sliding Window 优化)                      │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                                                          │  │
│  │  不每次都重算整个窗口, 使用增量更新:                        │  │
│  │                                                          │  │
│  │  current_count = prev_count + new_events_last_minute     │  │
│  │                   - events_expired_out_of_window          │  │
│  │                                                          │  │
│  │  维护一个环状缓冲区 (Ring Buffer):                         │  │
│  │  buffer[60] = 每分钟计数                                  │  │
│  │  ptr = (ptr + 1) % 60                                    │  │
│  │  window_sum = window_sum + buffer[new_ptr]               │  │
│  │               - buffer[old_ptr]                          │  │
│  └──────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

## 总结

| 维度 | 技术选型 | 理由 |
|------|---------|------|
| 消息队列 | Kafka | 高吞吐持久化 |
| 流处理 | Flink | 窗口聚合 + Checkpoint容错 |
| 实时计数 | Redis Sorted Set + Ring Buffer | 毫秒级 Top K 查询 |
| 近似计数 | Count-Min Sketch / SpaceSaving | 控制内存, 保证精度 |
| 长期存储 | ClickHouse | 高效时序数据存储和分析 |
| 热度算法 | 指数衰减 + 速度加权 | 兼顾热度和新鲜度 |
| 趋势检测 | Z-Score + 滑动窗口对比 | 区分稳定热和爆发热 |
| 话题规范化 | 规则 + 编辑距离 + 别名映射 | 同义话题聚合 |

核心设计要点:
1. **热度 = 计数 + 速度 + 新鲜度**: 纯计数会让老话题霸榜, 需要衰减和速度因子
2. **时间窗口是基础**: 分层窗口(1m → 5m → 1h)实现增量计算, 避免每次全量重算
3. **近似算法在大规模下是必要的**: Count-Min Sketch / SpaceSaving 在有限内存下提供可控精度的 Top K
4. **预计算优于实时计算**: 每分钟预计算 Top 1000 比每次查询时排序高效得多
5. **话题规范化是难点**: 同义合并直接影响榜单准确性
6. **数据分层存储**: 热数据(最近2h)在Redis, 温数据(24h)在ClickHouse, 冷数据(S3归档)
7. **防刷机制**: 需要配合反作弊(频率限制、异常检测), 否则容易被操纵
